# Episode 9 — product evidence rubric

Use this table when turning a hackathon system into a case study. One feature may occupy several rows; label each claim independently.

| Evidence class | Required receipt | Allowed language |
|---|---|---|
| Reproduced | command, environment, artifact, and dated pass | “We reproduced…” |
| Demonstrated | retained recording showing the complete path | “The demo showed…” |
| Source-reported | primary-source URL and capture date | “The source reports…” |
| Partial | working primitive plus named missing integration | “The primitive worked; integration remains…” |
| Failed | attempted path, failure layer, and retained error | “We attempted… and it failed because…” |
| Planned | design and acceptance gate, with no success implication | “We plan to…” |

## One-turn teardown

For a single user request, record:

1. The input and consent boundary.
2. The task chosen at each layer.
3. The model, runtime, and device placement.
4. The private context visible to every participant.
5. Any proposed tool effect and approval decision.
6. The returned answer, citations, and placement signal.
7. The artifacts that remain afterward and how they are deleted.

A prize is evidence that judges valued the submitted system. It is not evidence that every architectural claim passed independently.
