In this lesson we will draw OCR's findings on the page.
OCR returns boxes in pixels of the image it read; Redact's editor places marks in percentages of the page.
We'll convert one box by hand, run the tests that try to break the conversion, and then watch the outlines line up with the text.

**Checkpoint:** [`bcfd046`](https://github.com/danielAsaboro/bring-ai-home/commit/bcfd046e2ed1d5c33495263901034ef4c5361e01), starting from `30293ed`

## 2. Convert one box by hand

The chat image is 1200 pixels wide and 1600 pixels high.
In one run, OCR returned this box for `Maya Chen`:

```text
[211, 114, 397, 158]     x1, y1, x2, y2 in pixels
```

The first two numbers are the top-left corner and the last two are the bottom-right corner.
The editor wants a top-left corner plus a width and height, each as a percentage of the page:

```text
x      = 211 / 1200 × 100          = 17.583333
y      = 114 / 1600 × 100          = 7.125
width  = (397 − 211) / 1200 × 100  = 15.5
height = (158 − 114) / 1600 × 100  = 2.75
```

Notice the subtraction.
Dividing all four raw numbers by the page size would give a corner, not a size.

## 3. Check your arithmetic against the code

Open `src/features/redact/ocr-geometry.test.ts`.
The first test feeds exactly that box and page size into `normalizeOcrBbox` and expects:

```ts
{ x: 17.583333, y: 7.125, width: 15.5, height: 2.75 }
```

Your numbers should match.

## 4. Try to break it

Run only these tests:

```bash
npm test -- src/features/redact/ocr-geometry.test.ts
```

```text
Tests  3 passed (3)
```

Read what they cover: corners given in the wrong order are put back in order, a box hanging off the page is clipped to it, and a box with `NaN` in it, no area, or lying entirely off the page comes back as `null` and is skipped.
A page with a width of 0 throws an error instead, because then no box on it can be trusted.
